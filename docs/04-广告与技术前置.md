# 广告与技术前置

更新日期：2026-10-23

状态：方案与前置条件记录；未接入、未测试、未产生收益数据。

## 1. 用户约束与玩法提案

- 当前玩法提案为社区借物排期：两类物品、六个回合，时间覆盖 16:00—19:00，归还与到访预告公开；这些题材与数值尚待用户确认。
- 到访预告不是保证库存的承诺；到时变成当前请求，玩家确认借出才扣库存。自动动作仅为按时归还；19:00 仅清算归还，不再新借。
- 正常玩法必须独立成立，开始、排期、处理请求、结算、重开和进度记录不能依赖观看广告。
- 首版只考虑玩家主动点击的激励视频，不接插屏或 Banner，不自动展示广告。
- 广告只保留一个可选补救候选。奖励、可用时机、次数和冷却尚未定稿，不能将本文件视为已确认的最终规则。
- 本文件不包含游戏代码。任何 Lua 或其他游戏代码的创建、修改，仍须先说明文件与改动内容，等待用户确认。

## 2. 唯一奖励候选：临时调入一件短缺物品

候选含义：在 19:00 之前、当前请求仍处于合法处理窗口时，从明确的外部周转来源临时调入一件指定物品，用于帮助处理这一现存请求。借用需遵守同一截止归还规则，界面应提前展示物品种类、数量、目标请求和作用。

这不是已承诺有用的奖励。临时物品能否在该请求的使用时长与 19:00 截止约束内完成借出、归还，仍须结合最终规则验证。日末补库存不得被用来完成已经错过的请求；19:00 不提供新借入口。

这一候选需要先通过玩法验证，才能决定是否接入：

- 必须有一条明确的当前请求因该种物品短缺而受影响；不能为了展示广告生成新请求或制造短缺。
- 补给必须在当前时间线内合法生效。已经错过的请求、已经结束的回合和已经产生的结果不能被追溯改写。
- 不额外增加第七回合，不让临时物品提前出现在过去的排期中。
- 若当前操作规则无法合法使用这件物品，或调入后依然无法提供有意义的帮助，就不展示该候选。
- 临时物品必须记录外部来源，计入调入、借出及后续处置；不能无记录地增加本所自有库存。
- 临时调入物品的归还、退回外部来源及六回合内的记录方式，要在最终玩法确定时一并确认；不得放宽 19:00 截止规则。
- 允许拒绝观看并正常结算、重开；不得扣除本来已获得的结果，也不得隐藏正常入口。

若试验证明奖励很少有用、破坏排期决策，或必须增加新系统才能解释清楚，保持候选未接入并调整奖励或玩法，再验证。无广告版本可供内部测试，但未接入激励视频不满足本项目已确认的商业发布目标。不能为接入广告额外添加货币、体力、抽奖或经营养成。

## 3. 提示与频控

- 点击前说明完整观看的条件及具体奖励，不使用含糊的“领福利”替代说明。
- 拒绝、取消、提前关闭、无可用广告和加载失败都有明确反馈，游戏能够继续操作。
- 不用默认勾选、倒计时施压、误导按钮或遮挡正常结算入口促使观看。
- 广告期间保持当前局面；广告返回后重新确认局号、当前请求、处理时窗和奖励资格。
- 不向下一局或另一个借物请求发放上一广告请求的奖励。
- 单局次数、跨局冷却和是否存在每日限制均待玩法确认；当前不填写具体数值。
- 新手期广告开放时机需要单独设计，不因“主动点击”就认为可以任意展示。

## 5. 统一入口与奖励一致性要求

后续若接入，所有激励视频通过同一入口处理。这里列的是验收要求，不代表已经实现：

1. 发起前检查当前局、当前借物请求、短缺物品、可用时窗和频控资格；连续点击不能产生多个同时进行的广告请求。
2. 为一次广告请求保留独立身份，并关联局号、目标借物请求及固定奖励，不能根据回调时的界面状态猜测目标。
3. 只根据该版本 SDK 文档明确认可的完成结果发奖；展示成功、关闭、切回前台、经过一定时长都不能替代完成判定。
4. 同一请求重复回调只能结算一次；取消或失败后到达的迟到回调同样需要按已确认的 SDK 语义处理。
5. 奖励入账与领取记录应具备一致、可恢复的处理方式。具体方案取决于 SDK 与存储能力，当前不假定已有原子事务或可靠的完成凭证。
6. 应用中断后，不能仅因存在“待处理广告”记录就发奖；能否恢复确认须查文档并真机验证。
7. 不能因广告异常卡住结算；恢复操作不等于发放未经确认的奖励。
8. 没有可用广告时不伪造成功，也不承诺自动补发。

## 6. 接入顺序

1. 确认无广告玩法、六回合时间线及库存规则。
2. 证明候选奖励在当前规则下有意义，且无广告路线仍完整。
3. 获取并阅读当前项目的官方 devkit、Lua/sdk、存档及环境说明。
4. 核实账号、目标游戏、开通状态与配置；配置缺失时先解决缺口。
5. 向用户说明拟改的代码文件与内容，获得确认后实施。
6. 运行静态检查、逻辑测试与真机测试，再决定是否进入发布版本。
